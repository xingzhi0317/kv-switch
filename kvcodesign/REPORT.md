# 跨模型 KV 翻译的算法–系统协同设计：阶段报告（第一至四段）

> 计划见 `../PLAN_v4.md`。模型对 Qwen3-1.7B → Qwen3-4B。服务器 `~/kvcodesign/`，本目录是本地副本。
> 第二段（离线筛选）在 CPU 上完成；第一段（V 校准）和第三段（下游质量）在 GPU 4–7（及空出来的 0 号卡）上完成，见 §8。第四段（低秩结构的专用 kernel）见 §9，在一张 RTX 4090 上测。第五段以后还没开始。

## 0. 结论先行

**下游任务结论（§8，最重要）**：低秩共享潜空间"K 768 + V 1536"的计算量约为稠密的 1/6，在三个任务上和 kvbridge 稠密映射都没有显著差别（差值的 95% 区间都包含 0）。
秩 2048 的版本（计算量约 1/3.4）三项都不低于稠密。它也大幅好于补做了 V 校准的完整 CacheBridge。
所以离线读出误差上那 18% 的差距，在下游任务上看不出来。按"下游质量 ≥ 稠密、计算量 ≤ 2× head-local"的标准，低秩路线成立，可以进入写新 kernel 的阶段。

**kernel 结论（§9）**：为低秩结构写的专用 kernel，32K token 时 bf16 版 66ms、FP8 版 44ms（一张 4090），比 kvbridge 官方代码快约 12 倍，和 head-local kernel 一样快。加速大头来自算法本身的计算量下降，kernel 相对未融合实现再快 2.4 倍。融合 bf16 kernel 在 QuALITY 上和未融合版得分完全相同；FP8 版低 2.5 点，另外两个任务在重跑。

以下第 1–7 条是第二段离线筛选的结论：


1. **门槛没通过。** 计划的门槛是：乘加量 ≤ 2× head-local（1.51 亿），读出误差 ≤ 稠密映射。
   在这个预算内，最好的结构是"共享低秩潜空间，K 秩 768、V 秩 1536"，读出误差 **0.395**；
   公平的稠密基线是 **0.336**。差距约 18%。即使加到 2.7 亿乘加（3.6× head-local），读出误差也还有 0.365，仍没追平。
2. **但低秩潜空间明显优于 head-local。** 乘加量相近时（8400 万 vs 7550 万），读出误差 0.445 vs 0.701；
   计算量约为稠密 12 层映射的 1/11。
3. **RoPE 等变结构（方案二）不成立。** 只允许同频率混合后，K 的留出 R² 从 0.77 掉到 0.53，读出误差 > 0.9。跨频率混合是必要的。
4. **其他变体都更差。** K、V 共用一个潜空间；潜空间按目标层分 4 组；按"注意力实际关心的方向"加权降秩——都没有改进，或者更差。
5. **V 是瓶颈。** 把秩从 K 挪给 V 有效：同样 1.34 亿乘加，K 512 + V 1536 的读出误差是 0.405，K、V 各 1024 是 0.429。
6. **数值条件好，FP8 几乎无损。** 低秩映射的 K 权重范数约 20，head-local 约 1037。FP8 模拟（E4M3，激活按 token 缩放，权重按列缩放）下，
   读出误差只从 0.429 升到 0.434（r=1024）。作为对照，稠密映射在 FP8 下从 0.365 升到 0.380。
7. **CacheBridge V 校准的显存泄漏已修复并验证。** 36 层校准跑完，显存始终 10.9GB，见 §4。

## 1. 做法

- **数据**：上一阶段缓存的校准 KV（FineWeb-Edu 前 500 篇，每篇 1024 token，步长 4，共 116914 个位置，K 已去 RoPE）。
  按顺序取前 90% 训练、后 10% 验证。数据按文档顺序排列，所以这是文档级划分（只有边界上的一篇被切开）。
- **R²**：在验证行上算，K、V 分别按目标层平均。
  注意：kvbridge 官方权重和 CacheBridge 初始拟合用了全部 500 篇，它们的 R² 是样本内的，不能直接比较。
- **注意力读出误差**（主指标）：另取 FineWeb-Edu 第 500 篇以后的 16 篇满 1024 token 的文档，它们不在任何映射器的训练数据里。
  用目标模型真实的 Q，在第 256–1023 个位置上每隔 8 个取一个查询位置，用因果注意力分别读翻译 KV 和原生 KV，
  算 ‖o_翻译 − o_原生‖² / ‖o_原生‖²，再在 36 层上取平均。只预测均值的参考值是 1.43。
  （`collect_val.py`，在 CPU 上用 fp32 跑。）
- **求解**：先算一次全部 28 个源层 × 36 个目标层的中心化协方差（G：57344²，C：57344×73728），所有结构都从同一份统计量里闭式解出：
  - 稠密岭回归：K→K、V→V 分开，λ = α·mean(diag G)，α 在 1e-5 到 1e-1 之间扫，最优是 0.01；
  - 降秩岭回归：先求满秩岭回归解 W，再对 Wᵀ G W（即训练集上预测值的协方差）用随机子空间迭代取前 r 个方向 U，
    编码 P = W U，解码 Uᵀ。目标按"每个目标层同等重要"加权；
  - RoPE 等变 K：每个频率一个复数矩阵（224 个源单元 → 288 个目标单元）。它的正规方程正好是实数 G、C 的子块，不需要再过一遍数据。
- **公平的稠密基线**：用 kvbridge 自己选的 12 个源层、同样的 α，只在我们的训练集上重拟合（`dense12_refit`）。

## 4. CacheBridge V 校准的显存泄漏

`kvbase/fit_cb.py` 里，`q_states()` 在 `torch.no_grad()` 之外调用了目标模型的 `q_proj/k_proj/v_proj`，而模型参数默认 `requires_grad=True`。
所以 Q、K、V 带着计算图，残差 R 和特征 Dq 也带着计算图，`G += g` 让累加器 G 也开始带计算图。
结果是每个样本的整张图（包括保存的中间激活）都被挂在 G 上，直到这一层结束才释放。

这正好符合当时的现象：
- 每个样本泄漏固定大小；
- 内存里没有对应的 Python 张量；
- 内存快照里只有 C++ 调用栈（autograd 保存的张量）。

修复（`fit_cb2.py`，已放到服务器 `~/kvbase/`）：
- 两个模型都 `requires_grad_(False)`；
- 全局 `torch.set_grad_enabled(False)`；
- 每个样本后断言 G 不带梯度；
- 其余逻辑和官方校准代数不变。

**已在 GPU 上验证**：36 层全部校准完成，每层之后显存都停在 10.9GB（峰值 14.0GB），以前第 1 层就会爆显存。

## 9. 第四段：低秩结构的专用 kernel

### 9.1 做法

翻译分两步，每步一个 Triton kernel，bf16 和 FP8（E4M3）各一版（`fastlr.py`）：

1. **编码**：读源 cache（28 层 × 8 头 × 128 维，带 RoPE）→ 在读入时顺手去掉源模型的 RoPE → 乘编码矩阵 P → 得到每个 token 的潜向量（K 768 维、V 1536 维）。均值项预先折成一个偏置。
2. **解码**：潜向量乘解码矩阵 D → 加目标均值 → 在写出时直接加上目标模型的 RoPE，并按目标 cache 的布局（36 层 × 8 头 × 128 维）写出。

FP8 版：源 cache 每层一个静态缩放、潜向量一个静态缩放，都折进权重；权重按输出列缩放。缩放系数取自校准集的验证部分，没有用留出文档。

**和计划的出入**：计划里想把潜向量留在片上（共享内存），不写回显存，做成一个 kernel。实际没这么做，原因是算了一下不划算：
- 每个 token 的潜向量只有约 4.6KB（bf16），而源 cache 读入加目标 cache 写出约 270KB。潜向量写回再读一遍只多 3% 左右的访存。
- 这一步是算力瓶颈不是访存瓶颈（每 token 1.51 亿乘加），4090 上 bf16 矩阵乘的实测上限约 160 TFLOPS。
- 要留在片上，一个线程块就得同时负责全部 36 个目标层的输出，并行度和分块都很别扭。

所以拆成两个 kernel，把精力放在让两个矩阵乘都接近 cuBLAS 的速度上。主要的优化是线程块的执行顺序，让权重在 L2 缓存里被复用（编码按输出列最快变化排序，解码按行分组排序），这一步把 32K 的耗时从 85ms 降到 66ms。

### 9.2 正确性（16 篇留出文档）

| 实现 | 与 fp32 参考的相对误差 | 读出误差 |
|---|---|---|
| fp32 参考（PyTorch） | — | 0.3953 |
| PyTorch bf16（未融合，cuBLAS） | 3.8e-3 | 0.3954 |
| **融合 kernel bf16** | 2.4e-3 | 0.3951 |
| **融合 kernel FP8** | 3.1e-2 | 0.3978 |

融合 bf16 比未融合的 PyTorch bf16 还略准（RoPE 在 fp32 里算）。FP8 读出误差只升 0.6%。
把多个请求拼在一起送进 kernel，输出和逐个翻译逐位一致。

- 低秩融合 bf16 比 kvbridge 官方代码快约 12 倍，比我们上一阶段的稠密融合 kernel 快约 10 倍，比未融合的低秩快 2.4 倍。
- 低秩融合 bf16 和 head-local 融合 kernel 几乎一样快（66 vs 63ms），但下游质量远好（§8）。FP8 版比 head-local 还快 30%。
- 吞吐：bf16 约 50 万 token/s，FP8 约 75 万 token/s。

**加速的来源要说清楚**：大头来自算法（计算量降到稠密的约 1/6），kernel 本身相对未融合的 cuBLAS 实现快 2.4 倍（主要是省掉去 RoPE / 加 RoPE / 换布局这些额外的读写，以及 FP8）。

### 9.4 局限

- **短请求效率低。** 512 token 时一次翻译约 2.3ms，算力利用很低：矩阵太扁，线程块不够把 GPU 填满。CUDA graph 没有帮助（瓶颈不是启动开销）。之后可以试 split-K，或者把多个短请求拼成一批（已验证拼接结果正确）。
- 只在 4090 上测过，没在 H100 等卡上测。

### 9.5 融合 kernel 的下游结果

| 实现 | QuALITY（200 题） | 和 kvbridge 的差 [95% 区间] |
|---|---|---|
| 低秩 PyTorch bf16（§8） | 47.0% | −3.0 [−8.0, +2.0] |
| **融合 kernel bf16** | **47.0%** | −3.0 [−8.0, +2.0] |
| **融合 kernel FP8** | 44.5% | −5.5 [−11.0, 0.0] |

- 融合 bf16 和未融合 bf16 的得分完全相同，说明 kernel 没有带来精度损失。
- FP8 比 bf16 低 2.5 点，超出噪声带（0.5 点），和 kvbridge 的差的区间上端碰到 0。FP8 版在 QuALITY 上可能有轻微损失，需要看另外两个任务再下结论。
- HotpotQA 和 GSM8K 两个任务跑到一半时，服务器上别人的任务占满了所有卡，我们的进程被挤掉（HotpotQA 显存不足，GSM8K 进程被终止）。已经排进等待队列，有空卡后自动重跑。中途的部分结果（HotpotQA 180 题：bf16 0.329、FP8 0.302，kvbridge 0.324）仅供参考。

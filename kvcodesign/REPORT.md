## 0. 结论先行

**下游任务结论（§8，最重要）**：低秩共享潜空间"K 768 + V 1536"的计算量约为稠密的 1/6，在三个任务上和 kvbridge 稠密映射都没有显著差别（差值的 95% 区间都包含 0）。
秩 2048 的版本（计算量约 1/3.4）三项都不低于稠密。它也大幅好于补做了 V 校准的完整 CacheBridge。
所以离线读出误差上那 18% 的差距，在下游任务上看不出来。按"下游质量 ≥ 稠密、计算量 ≤ 2× head-local"的标准，低秩路线成立，可以进入写新 kernel 的阶段。

**kernel 结论（§9）**：为低秩结构写的专用 kernel，32K token 时 bf16 版 66ms、FP8 版 44ms（一张 4090），比 kvbridge 官方代码快约 12 倍，和 head-local kernel 一样快。加速大头来自算法本身的计算量下降，kernel 相对未融合实现再快 2.4 倍。融合 bf16 kernel 在 QuALITY 上和未融合版得分完全相同；FP8 版低 2.5 点，另外两个任务在重跑。

以下第 1–7 条是第二段离线筛选的结论：


1. **门槛没通过。** 计划的门槛是：乘加量 ≤ 2× head-local（1.51 亿），读出误差 ≤ 稠密映射。
   在这个预算内，最好的结构是"共享低秩潜空间，K 秩 768、V 秩 1536"，读出误差 **0.395**；
   公平的稠密基线是 **0.336**。差距约 18%。即使加到 2.7 亿乘加（3.6× head-local），读出误差也还有 0.365，仍没追平。
2. **但低秩潜空间明显优于 head-local。** 乘加量相近时（8400 万 vs 7550 万），读出误差 0.445 vs 0.701；
   计算量约为稠密 12 层映射的 1/11。
3. **RoPE 等变结构（方案二）不成立。** 只允许同频率混合后，K 的留出 R² 从 0.77 掉到 0.53，读出误差 > 0.9。跨频率混合是必要的。
4. **其他变体都更差。** K、V 共用一个潜空间；潜空间按目标层分 4 组；按"注意力实际关心的方向"加权降秩——都没有改进，或者更差。
5. **V 是瓶颈。** 把秩从 K 挪给 V 有效：同样 1.34 亿乘加，K 512 + V 1536 的读出误差是 0.405，K、V 各 1024 是 0.429。
6. **数值条件好，FP8 几乎无损。** 低秩映射的 K 权重范数约 20，head-local 约 1037。FP8 模拟（E4M3，激活按 token 缩放，权重按列缩放）下，
   读出误差只从 0.429 升到 0.434（r=1024）。作为对照，稠密映射在 FP8 下从 0.365 升到 0.380。
7. **CacheBridge V 校准的显存泄漏已修复并验证。** 36 层校准跑完，显存始终 10.9GB，见 §4。

## 1. 做法

- **数据**：上一阶段缓存的校准 KV（FineWeb-Edu 前 500 篇，每篇 1024 token，步长 4，共 116914 个位置，K 已去 RoPE）。
  按顺序取前 90% 训练、后 10% 验证。数据按文档顺序排列，所以这是文档级划分（只有边界上的一篇被切开）。
- **R²**：在验证行上算，K、V 分别按目标层平均。
  注意：kvbridge 官方权重和 CacheBridge 初始拟合用了全部 500 篇，它们的 R² 是样本内的，不能直接比较。
- **注意力读出误差**（主指标）：另取 FineWeb-Edu 第 500 篇以后的 16 篇满 1024 token 的文档，它们不在任何映射器的训练数据里。
  用目标模型真实的 Q，在第 256–1023 个位置上每隔 8 个取一个查询位置，用因果注意力分别读翻译 KV 和原生 KV，
  算 ‖o_翻译 − o_原生‖² / ‖o_原生‖²，再在 36 层上取平均。只预测均值的参考值是 1.43。
  （`collect_val.py`，在 CPU 上用 fp32 跑。）
- **求解**：先算一次全部 28 个源层 × 36 个目标层的中心化协方差（G：57344²，C：57344×73728），所有结构都从同一份统计量里闭式解出：
  - 稠密岭回归：K→K、V→V 分开，λ = α·mean(diag G)，α 在 1e-5 到 1e-1 之间扫，最优是 0.01；
  - 降秩岭回归：先求满秩岭回归解 W，再对 Wᵀ G W（即训练集上预测值的协方差）用随机子空间迭代取前 r 个方向 U，
    编码 P = W U，解码 Uᵀ。目标按"每个目标层同等重要"加权；
  - RoPE 等变 K：每个频率一个复数矩阵（224 个源单元 → 288 个目标单元）。它的正规方程正好是实数 G、C 的子块，不需要再过一遍数据。
- **公平的稠密基线**：用 kvbridge 自己选的 12 个源层、同样的 α，只在我们的训练集上重拟合（`dense12_refit`）。

## 4. CacheBridge V 校准的显存泄漏

`kvbase/fit_cb.py` 里，`q_states()` 在 `torch.no_grad()` 之外调用了目标模型的 `q_proj/k_proj/v_proj`，而模型参数默认 `requires_grad=True`。
所以 Q、K、V 带着计算图，残差 R 和特征 Dq 也带着计算图，`G += g` 让累加器 G 也开始带计算图。
结果是每个样本的整张图（包括保存的中间激活）都被挂在 G 上，直到这一层结束才释放。

这正好符合当时的现象：
- 每个样本泄漏固定大小；
- 内存里没有对应的 Python 张量；
- 内存快照里只有 C++ 调用栈（autograd 保存的张量）。

修复（`fit_cb2.py`，已放到服务器 `~/kvbase/`）：
- 两个模型都 `requires_grad_(False)`；
- 全局 `torch.set_grad_enabled(False)`；
- 每个样本后断言 G 不带梯度；
- 其余逻辑和官方校准代数不变。

**已在 GPU 上验证**：36 层全部校准完成，每层之后显存都停在 10.9GB（峰值 14.0GB），以前第 1 层就会爆显存。

## 9. 第四段：低秩结构的专用 kernel

### 9.1 做法

翻译分两步，每步一个 Triton kernel，bf16 和 FP8（E4M3）各一版（`fastlr.py`）：

1. **编码**：读源 cache（28 层 × 8 头 × 128 维，带 RoPE）→ 在读入时顺手去掉源模型的 RoPE → 乘编码矩阵 P → 得到每个 token 的潜向量（K 768 维、V 1536 维）。均值项预先折成一个偏置。
2. **解码**：潜向量乘解码矩阵 D → 加目标均值 → 在写出时直接加上目标模型的 RoPE，并按目标 cache 的布局（36 层 × 8 头 × 128 维）写出。

FP8 版：源 cache 每层一个静态缩放、潜向量一个静态缩放，都折进权重；权重按输出列缩放。缩放系数取自校准集的验证部分，没有用留出文档。

**和计划的出入**：计划里想把潜向量留在片上（共享内存），不写回显存，做成一个 kernel。实际没这么做，原因是算了一下不划算：
- 每个 token 的潜向量只有约 4.6KB（bf16），而源 cache 读入加目标 cache 写出约 270KB。潜向量写回再读一遍只多 3% 左右的访存。
- 这一步是算力瓶颈不是访存瓶颈（每 token 1.51 亿乘加），4090 上 bf16 矩阵乘的实测上限约 160 TFLOPS。
- 要留在片上，一个线程块就得同时负责全部 36 个目标层的输出，并行度和分块都很别扭。

所以拆成两个 kernel，把精力放在让两个矩阵乘都接近 cuBLAS 的速度上。主要的优化是线程块的执行顺序，让权重在 L2 缓存里被复用（编码按输出列最快变化排序，解码按行分组排序），这一步把 32K 的耗时从 85ms 降到 66ms。

### 9.2 正确性（16 篇留出文档）

| 实现 | 与 fp32 参考的相对误差 | 读出误差 |
|---|---|---|
| fp32 参考（PyTorch） | — | 0.3953 |
| PyTorch bf16（未融合，cuBLAS） | 3.8e-3 | 0.3954 |
| **融合 kernel bf16** | 2.4e-3 | 0.3951 |
| **融合 kernel FP8** | 3.1e-2 | 0.3978 |

- 低秩融合 bf16 和 head-local 融合 kernel 几乎一样快（66 vs 63ms），但下游质量远好（§8）。FP8 版比 head-local 还快 30%。
- 吞吐：bf16 约 50 万 token/s，FP8 约 75 万 token/s。

**加速的来源要说清楚**：大头来自算法（计算量降到稠密的约 1/6），kernel 本身相对未融合的 cuBLAS 实现快 2.4 倍（主要是省掉去 RoPE / 加 RoPE / 换布局这些额外的读写，以及 FP8）。

### 9.4 局限

- **短请求效率低。** 512 token 时一次翻译约 2.3ms，算力利用很低：矩阵太扁，线程块不够把 GPU 填满。CUDA graph 没有帮助（瓶颈不是启动开销）。之后可以试 split-K，或者把多个短请求拼成一批（已验证拼接结果正确）。
- 只在 4090 上测过，没在 H100 等卡上测。

### 9.5 融合 kernel 的下游结果

| 实现 | QuALITY（200 题） | 和 kvbridge 的差 [95% 区间] |
|---|---|---|
| 低秩 PyTorch bf16（§8） | 47.0% | −3.0 [−8.0, +2.0] |
| **融合 kernel bf16** | **47.0%** | −3.0 [−8.0, +2.0] |
| **融合 kernel FP8** | 44.5% | −5.5 [−11.0, 0.0] |

- 融合 bf16 和未融合 bf16 的得分完全相同，说明 kernel 没有带来精度损失。
- FP8 比 bf16 低 2.5 点，超出噪声带（0.5 点），和 kvbridge 的差的区间上端碰到 0。FP8 版在 QuALITY 上可能有轻微损失，需要看另外两个任务再下结论。
- HotpotQA 和 GSM8K 两个任务跑到一半时，服务器上别人的任务占满了所有卡，我们的进程被挤掉（HotpotQA 显存不足，GSM8K 进程被终止）。已经排进等待队列，有空卡后自动重跑。中途的部分结果（HotpotQA 180 题：bf16 0.329、FP8 0.302，kvbridge 0.324）仅供参考。

文件：`fastlr.py`（kernel 和封装）、`test_fastlr.py`（正确性、FP8 缩放）、`prof_fastlr.py`（分 kernel 调参）、`bench_fastlr.py`（延迟）、`test_batch_graph.py`（拼批、CUDA graph）；结果 `results/fastlr_*.json`。

## 11. 第一段：精确信息评测（Qwen3-1.7B → Qwen3-4B）

### 11.1 结论

1. **只要答案必须是历史里的精确内容，所有翻译方法都大幅失败。** 两个模型自己读都接近满分的题（数字口令、键值检索），翻译后只剩 2%–25%。
   五个新任务加上"题目经过翻译的 GSM8K"，最好的翻译方法都明显低于 4B 原生（差 36–91 个点，95% 区间都不含 0）。**第一段门槛通过。**
2. **翻译后远低于小模型自己答。** 1.7B 原生在这些任务上是 78%–100%，说明信息在源 cache 里是有的，丢在翻译这一步。
3. **稠密翻译同样失败**：kvbridge（官方权重）在键值检索上 7.5%，数字口令 3%–7%。所以这不是低秩造成的。
4. **错的方式是"能定位、抄不准"。** 2K 数字口令里，翻译后的模型 89%–98% 的题前 3 位是对的，但 6 位数大多只写出 4–5 位（漏位），平均前 4–5 位正确。
   这和 arXiv 2611.12062 在混合注意力模型上报告的现象一致；我们是在标准注意力（GQA）、闭式映射上看到的。
5. **加秩有帮助但远远不够。** K、V 各 2048 的低秩在数字口令上是 19%–25%，显著高于 kvbridge（+15 到 +21 点）和主力档 K768+V1536（5%–7%），但离原生的 100% 还差 75 点以上。
6. 低秩主力档在抽取问答和 GSM8K（题目经过翻译）上显著低于 kvbridge（−18 点、−15 点）；在数字口令上和 kvbridge 打平（两者都接近 0）。
7. **截断不是原因。** 数字类任务最初生成上限是 16 token，翻译方法有 50%–73% 的回答被截断；上限改成 64 后截断率降到 0–2%，但得分完全不变（被截掉的只是数字后面的 `**.`）。

### 12.1 依赖图：稠密解里每个目标（层，头）读的是哪些源（层，头）

图：`results/depgraph.png`；脚本 `depgraph.py`。把稠密解按 224 个源块 × 288 个目标块切开，用源协方差加权算每块对预测的贡献。

- **K 按深度对应。** 每个目标层读的源层重心和相对深度的相关系数是 0.97；相对深度 ±2 层内的源层占 48% 的贡献（随机是 18%）。约 5 个源层覆盖一半贡献，约 17 个覆盖 90%。
- **V 是"按深度对应 + 公共源"。** 目标层 16 以后按深度对应；但源模型第 18–22 层给几乎所有目标层都供了不少（它们合计占总贡献的 42%），目标前 7 层最大的来源反而是源第 20 层。

## 13. 第三段第一步：加入 token 身份（负结果）

做法（闭式、不训练，`fit_tid.py`）：
- 目标模型第 0 层的 K、V 只取决于 token，直接精确算出（和模型真实产生的只差万分之二），不再翻译。
- 把它作为额外输入特征加进低秩映射，重新做闭式降秩岭回归（目标是第 1–35 层）。
- 坑：身份特征会把每段历史的第一个 token（注意力汇聚点）的 V 搞坏（相对误差 0.44 → 1.99，读出误差 0.37 → 0.54，`diag_tid.py`），所以第一个 token 仍用不带身份的映射。

离线（留出数据，第 1–35 层）：V 的 R² 0.609 → 0.617（稠密）、0.589 → 0.595（低秩主力档）；数字 token 的 V 误差 0.486 → 0.477。几乎没有变化。

下游（和 kvbridge 逐题配对；抽取问答只跑完 180 题，其余完整）：

| 方法 | 抽取问答 F1 | 键值检索 | 口令 2K | 口令 8K |
|---|---|---|---|---|
| kvbridge（参照，§11） | 0.466 | 7.5% | 7.0% | 3% |
| kvbridge + 第 0 层精确 | 0.481（+0.010 [−0.004, +0.026]） | 16.0%（+8.5 [+5.0, +12.5]） | 7.5% | 4% |
| 低秩 K768+V1536 + 第 0 层精确 | 0.288 | 2.0% | 8.0% | 5% |
| 低秩 K768+V1536 + 身份特征 | 0.304 | 1.5% | 9.0% | 6% |
| 低秩 K、V 各 2048 + 身份特征 | 0.355 | 9.5% | 29.0% | 30% |

结论：**闭式映射里加 token 身份基本没用。** 只有两处小的改善：kvbridge 的键值检索 7.5% → 16%，低秩 2048 的口令 24% → 29–30%，都离原生的 94–100% 很远。线性映射缺的不是"这是哪个 token"，而是和上下文相关的那部分。
这和 arXiv 2611.12062 的全文一致：它在标准注意力的 Qwen3-8B↔4B 上不需要 token 身份，靠的是穿过冻结目标模型的 KL 微调（口令召回 1.00，只测到 2–8K）；token 身份只对压缩型 cache 有用。PLAN_v5 §3 对这篇的描述需要按此更正。

GSM8K、QuALITY、HotpotQA、16K 口令上的这组评测没有跑（方法已判定无效，停掉以节省显卡）。

计划见 `../PLAN_v6.md`。目标是把已有方法都画到"精度 × 首字时延"二维图上，看帕累托前沿的形状，再定我们往哪里推。

### 15.0 结论先行

1. **同一底座的两个模型之间切换，基本已经解决。** Qwen3-1.7B-Base → Qwen3-1.7B：
   - 一层都不重算、直接复用对方的 KV，就保留了阅读理解 88%、精确信息 95%，首字加速 12 倍（16K 历史）。
   - DroidSpeak 再重算一部分层，精度接近完整重读。
2. **不同尺寸之间（1.7B ↔ 4B）还差得很远**，这里才是值得做的地方。所有翻译类方法的精确信息保留率都在 53% 以下；保留率高的文本类方法和重算类方法，又几乎没有加速，甚至比重读还慢。前沿中间有一大片空白。
3. **我们的低秩共享潜空间在两个方向的三张图上都在前沿上**：
   - 小换大：融合 kernel 版加速 12 倍，是翻译类方法里最快的；阅读理解保留 61%，和 kvbridge（62%，加速 3.7 倍）持平。
   - 大换小：秩 2048 版的精确信息保留 53%，是**所有方法里最高的**，同时加速 3.1 倍。
4. **KL 训练（KV-Lingo / Hybrid-KV 的做法）能补一部分精确信息，但不是全面提升。**
   - 口令任务提升明显（例如大换小 2K 口令从 0% 到 47.5%），大换小的续写 KL 降到 0.37，是翻译类方法里最好的。
   - 但阅读理解反而下降，小换大的抽取问答也变差。离论文报告的口令 1.00 还很远。
5. **CacheBridge 在两个方向都失效**（续写 KL 比"不看历史"还差），和之前拟合时 V 校准残差能量爆掉的现象一致。

### 15.1 设定

- **模型对**：
  - Qwen3-1.7B → Qwen3-4B（弱换强，下称"小换大"）；
  - Qwen3-4B → Qwen3-1.7B（强换弱，下称"大换小"）；
  - Qwen3-1.7B-Base → Qwen3-1.7B（同一底座，DroidSpeak 的设定）。
- **精度**：
  - 保留率 = 方法得分 ÷ 完整重读得分，分两组取平均：
    - 阅读理解：QuALITY 200 题、LongBench HotpotQA-E 200 题；
    - 精确信息：SQuAD 200 题、问题放在历史里的 GSM8K 200 题、键值检索 200 题、2K 口令 200 题、8K 口令 100 题。
  - 续写 KL：Nemotron-SFT-Instruction-Following-Chat-v2 的 200 段对话（8K 历史时 100 段）。历史截到 2K / 8K token，把接下来 128 个 token 喂进去，算每一步输出分布相对原生的 KL。图上画成 exp(−KL)×100。
- **首字时延**：
  - 计时起点：新模型拿到旧模型的 cache；终点：读完 128 token 的新消息、吐出第一个字。中间每个方法要做的事（翻译、重算、压缩、总结、重读）都计入。
  - 一张 RTX 4090；HF transformers + sdpa，不开 CUDA graph（老师确认先用普通 HF）。
  - 每个方法单独一个进程测，7 次取中位数（前 2 次预热）。测量期间如果有别人的任务上了同一张卡，这次作废重测；最终数据里没有作废记录。
- **方法**：
  - 重读、不看历史；
  - 文本类：旧模型先总结（压到原长 10%）、LLMLingua-2 压缩到 25% / 50%；
  - 翻译类：kvbridge（NVIDIA 官方代码，每层用 12 个源层）、CacheBridge（官方代码 + 补写的 V 校准）、KL 训练翻译器（我们按 KV-Lingo / Hybrid-KV 复现：每层用 3 个源层的闭式解做初值，再穿过冻结的新模型做 2000 步 KL 蒸馏）、我们的低秩（K 768 + V 1536 融合 kernel；秩 2048）；
  - 重算类：RaReCache 重算 10% / 30% / 50% 的 token（按论文复现，翻译用 kvbridge）、DroidSpeak（按论文复现，见 §15.4）。
- 32K 历史时，所有翻译类方法在 24GB 卡上显存不足：两个模型、源 cache、翻译出的 cache 同时放不下。所以图用 16K。

### 15.4 同一底座（1.7B-Base → 1.7B）：DroidSpeak

DroidSpeak（arXiv 2411.02820）要求两个模型来自同一个底座、结构和宽度完全一样，原文明确说不支持不同底座的模型。所以 1.7B ↔ 4B 用不了，另选这一对。论文没有公开代码，按原文复现（`droid.py`）：

- 新模型复用旧模型每一层的 KV，只有一段**连续的层**自己重算。重算的输入是旧模型在这一段第一层的输入隐藏状态（论文叫 E cache）。
- 论文没写清、我们自己定的：
  - E cache 取进入这一层的残差流；
  - 重算段之后的层也直接复用旧模型的 KV；
  - 只重算历史 token，新消息照常由新模型读；
  - E cache 和 KV 一起预先存好，不计入首字时延。
- 自检：两边用同一个模型时，任何重算段的结果都和原生完全一致（续写 KL 为 0）。
- 挑层（同论文）：用 50 条 HotpotQA（第 200–249 题，和评测的前 200 题不重叠），以 2 层为单位枚举全部 105 个连续段，取 F1 下降不超过 5% 且重算层数最少的一段。结果是**重算第 4–19 层（28 层中的 16 层）**，F1 达到原生的 99.6%；完全复用只有 63%。论文里一般只需重算 10%–25% 的层，这一对需要的多得多。
- 反方向（1.7B → Base）测不出东西：Base 模型不会按对话格式作答，自己读完整历史的 HotpotQA F1 也只有 0.07。已停掉。

完整重读 689ms（新模型同为 1.7B，和 §15.3 的 701ms 是分别测的）。

| 方法 | 加速 | 阅读理解 | 精确信息 | 续写 KL（2K / 8K） |
|---|---|---|---|---|
| 不看历史 | 21 倍 | 52% | 0% | 1.52 / 1.67 |
| 完全复用（一层不重算） | **12 倍** | 88% | 95% | 0.16 / 0.14 |
| 重算 8 层（第 4–11 层） | 2.9 倍 | 93% | 97% | 0.13 / 0.12 |
| 重算 12 层（第 4–15 层） | 2.0 倍 | 93% | 104% | 0.09 / 0.09 |
| 重算 16 层（第 4–19 层，挑层选中） | 1.6 倍 | 96% | 102% | 0.06 / 0.06 |
| LLMLingua 25% | 0.96 倍 | 77% | 43% | 1.08 / 1.15 |
| LLMLingua 50% | 0.76 倍 | 89% | 49% | 0.81 / 0.83 |

- 精确信息能超过 100%：8K 口令上，1.7B 自己读只对 83%，用 Base 的 KV 反而对 96–100%。
- 这一对上直接复用就已经很好，DroidSpeak 的重算只再补几个百分点，代价是加速从 12 倍掉到 1.6–2.9 倍。

**朴素版 DroidSpeak 放到不同尺寸上（1.7B ↔ 4B，负结果，不画进图）**：
- 两个模型每层 KV 的形状碰巧一样（8 个头 × 128 维），所以试了不经翻译直接复用：层数不同就按深度比例对应；宽度不同、拿不到对方的中间隐藏状态，所以只能从第 0 层开始重算前 b 层（`droid.py` 的 `dsx_direct_{b}`）。自检：b 等于全部层数时和原生完全一致。
- 结果：直接复用的续写 KL 约 15（不看历史是 1.7），比不看历史差得多。
- 按论文的方法挑层（50 条 HotpotQA，2 层为单位）：
  - 小换大：重算 34/36 层时 F1 只到原生的 14%；
  - 大换小：重算 26/28 层时 F1 到 93%；
  - 两个方向都要重算全部层才满足"下降不超过 5%"，等于完整重读。
- 原因：两个模型分别从头训练，KV 的坐标系互不相关（§12 的诊断里，同号头的对应率 12.6%，和随机的 12.5% 一样）。只要还有一层用的是对方的 KV，新消息读到这一层就会被带偏。所以 DroidSpeak 只适用于同一底座；不同尺寸之间必须先翻译。
- 评测只跑了一部分就停了（结果文件 `results/*_dsx.json`、`results/dsx_*.json`），图上不放。

### 15.5 这说明了什么、下一步

- **问题的难点在不同尺寸之间。** 同底座时 KV 几乎可以直接互用；1.7B ↔ 4B 时，最好的翻译方法也只保留约一半的精确信息。
- **前沿上"高加速"那一段被我们的低秩占着**，但精确信息还低。要往外推，就是在不牺牲太多加速的前提下把精确信息补上来。可选的路：
  1. 在低秩结构里做 KL 微调（§14 的配方）。本节的 KL 训练翻译器说明 KL 训练能补口令类信息，但会伤阅读理解，要一起看。
  2. "翻译 + 前缀层重算"：DroidSpeak 式的按层重算，改造到不同尺寸上（先翻译，再让新模型从第 0 层重算前若干层），和 RaReCache 的"按 token 重算"直接比较。这一条还没人做，可能是我们的贡献点。
- **还没做的**：CoQA 多轮对话、跨家族模型对、32K（需要更大显存，或者翻译和读取分块流水）。

## 16. CacheBridge 复现：小模型对、论文自己的模型对、逐条对齐

CacheBridge（arXiv 2609.00891，v2 2026-11-03）。论文在 Qwen3 8B→14B 上报告 QuALITY 保留率：不校准 62%，校准后 97%。公开代码只有 14B→32B 的配方，**按 R² 选源层**和**带能量约束的 V 校准**两部分没有公开，按论文附录 B 自己实现（`fit_cb4.py`，后改写为 `fit_cb6.py`）。

### 16.1 1.7B → 4B（小换大）

| 版本 | QuALITY | HotpotQA | SQuAD（论文写法） | GSM8K |
|---|---|---|---|---|
| 论文原样：逐头 8 层，不校准 | 44% | 12% | — | 0% |
| 论文原样：逐头 8 层 + 能量约束校准 | 58%* | 24%* | 18% | 7%* |
| 变体：全头 3 层 + 校准 | 61%* | 29%* | 39%* | 11%* |
| 变体：全头 12 层 + 校准 | 73% | 56% | 67% | 55% |
| kvbridge（全头 12 层，不校准） | 70% | 53% | 64% | 48% |
| 低秩 r2048 | 74% | 54% | 74% | 44% |

带 * 的是 50 题，其余 200 题。全头 12 层变体在 Pareto 图上和 kvbridge 同速（3.0 倍），三张图都和 kvbridge 持平或略高，没有压过低秩：阅读理解和 r2048 打平（r2048 快 1.7 倍），精确信息 26% 对 r2048 的 29%。

- **起作用的是每个目标头能看到多少源信息**：逐头 8 层 = 8 个源向量，全头 3 层 = 24 个，全头 12 层 = 96 个，保留率按这个顺序上升。校准在 12 层上只多 2–3 个点。

### 16.2 同编号头没有对应关系（两对模型都没有）

`head_corr.py`：同一份数据（kvbridge 的采样方式，500 段 FineWeb-Edu），对每个目标层取最佳源层，算单头回归 R²；再用前 8 个源层的全部头做联合回归，看同编号头贡献的比例。

| 指标（K / V） | 1.7B→4B | 8B→14B | 随机 |
|---|---|---|---|
| 同编号头单头 R² | 0.485 / 0.247 | 0.487 / 0.230 | — |
| 其他编号头单头 R² | 0.480 / 0.241 | 0.484 / 0.223 | — |
| 8 个源头中同编号头排第一 | 16% / 16% | 12% / 14% | 12.5% |
| 联合回归中同编号头的贡献 | 12.8% / 12.5% | 12.7% / 12.8% | 12.5% |

浅、中、深三段分开看也都在 11–14%。所以"大模型对之间有头对应、小模型没有"不成立，CacheBridge 的逐头设计在两对上都只拿到每层 1/8 的信息。

### 16.3 论文自己的模型对：Qwen3-8B → 14B

14B 拆在两张卡上（`eval_quality.py DIR=8to14`），8B 和映射在第三张卡。QuALITY 200 题，排除 24 篇校准文章。

**第一轮（我们原来的提示和数据）**

| 方法 | 保留率（95% 范围） | 论文 |
|---|---|---|
| 不看历史 | 50% | — |
| 不校准 | 52%（44–61%） | 62% |
| 校准，能量上限 1%（论文设定） | 57%（48–66%） | 97% |
| 上限 10% | 64%（56–73%） | — |
| 上限 100% | 73%（65–82%） | — |
| 不约束 | 75%（67–83%） | — |

能量上限是主要瓶颈：不约束时校准想做的修正约是初始误差的 4 倍，1% 的上限只允许其中约 1/400。8B→14B 上不约束没有发散。

**第二轮：论文公开的细节逐条对齐后**

对齐了四处：
1. 提示按论文表 6：历史 = 简短作答指令 + 完整文章，问题 = 题目 + 四个选项 + `Answer:` + 对话模板结尾。新任务 `quality_cb`，校准和评测用同一个函数生成提示。
2. 校准用完整文章。之前截断到 6000 token，24 篇里有 14 篇被截。
3. 能量约束的 M 和 E0 在初始拟合的 FineWeb 数据上算（4096 个位置）。之前是在 QuALITY 文章上算的。
4. 初始拟合只用满 1024 token 的文本，正好 128,000 个位置；选层用全部位置。

| 方法 | 正确率 | 保留率（95% 范围） | 论文 |
|---|---|---|---|
| 14B 自己重读 | 0.795 | 100% | 80.49 |
| 不看历史 | 0.24 | 30%（23–38%） | — |
| 不校准 | 0.37 | 47%（38–55%） | 62% |
| **校准，上限 1%（论文设定）** | **0.48** | **60%（52–70%）** | **97%** |
| 校准，不约束 | 0.545 | 69%（60–77%） | — |

已核对和论文一致的：打分（A–D 四个字母的概率）、保留率定义、选层打分（同编号头 K、V 的 R² 平均，取前 8 层）、岭系数 0.01、校准数据（24 篇 × 4 题，问题部分全部位置）、校准加权（官方 `gram` 按 token 和 GQA 头平均，和论文的 1/(4·g·m) 只差常数）、校准正则 0.01·tr(G)/p、FP64 按头求解、能量约束定义。

**结论**：评测设定已对齐（14B 重读 79.5 对 80.5），但 CacheBridge 校准后是 60% 对论文的 97%，不校准是 47% 对 62%。差距远大于误差，问题出在论文没有公开的部分，初始映射这一步就差了 15 个点。不是模型大小的问题。

另外两点观察：
- 论文表 25 里不校准那组的原始分（59.38、46.88、53.13、81.25、6.25、50.00）恰好都是 x/32 的形式。我们曾怀疑这组消融只用了 32 题；作者回复（2026-11-20）说 v2 版没有用这么小的子集评测，以作者说法为准。
- 作者确认的三处细节（E0、M 在 FineWeb 初始化数据上每层每头算、对 token 平均、头内各维求和；初始化 500 × 1024、步长 4；选层用同编号头 K、V 的 R² 对所有头平均、每层 top-8、K/V 共用），对齐版都已经是这样做的。映射器和数据要等审稿后公开。

## 17. CacheBridge 复现收尾、校准推广到低秩、8B→14B 上的低秩

### 17.0 结论先行

1. **论文的 97% 复现不出来，CFM 基线明显偏弱。** Qwen3-8B→14B、QuALITY 全部 1645 道评测题上：CacheBridge 不校准 51%、校准后 63%，论文分别是 62% 和 97%；官方 kvbridge 代码的 CFM 是 84%，论文报告 44%。论文 CFM 的 R² 和分数，与每层只选 2–4 个源层的 CFM 对得上。
2. **校准是通用的好方法，但修不好逐头映射。** 8B→14B 上，同样 8 层、同样 1% 校准，HotpotQA 保留率为：逐头 36%（比不看历史还差），全头 74%，低秩 79%。
3. **我们的低秩加校准在两对模型上都处在前列，而且计算量小。**
   - 1.7B→4B：低秩 2048 + 校准的阅读理解 64.7%、精确信息 31.0%，都是翻译类方法里最高的，首字加速 5.1 倍。
   - 8B→14B：QuALITY 85%、HotpotQA 79%。HotpotQA 是所有方法里最高的，QuALITY 和最好的"全头 8 层 + 校准"（88%）打平，计算量只有它的一半。
4. **能量约束要取中间值，而且不能只看 QuALITY 来选。** 约束越松，QuALITY 越高，但密码、续写会先后变差。验证集选出来的档位，在测试集上和 1% 没有区别。

### 17.2 校准提速

| 脚本 | 内容 | 耗时 |
|---|---|---|
| `fit_cb6.py` | 逐头校准，逐层传递 | 1.7B→4B 2 小时 → 3.5 分钟；8B→14B 4.6 分钟 |
| `fit_cb7.py` | 全头校准，逐层传递；所有头共用一个 M；求解用 fp32 Cholesky + fp64 迭代修正 | 8B→14B 全头 8 层：不约束 7 分钟，1% 约 23 分钟 |
| `fit_lrc.py` / `fit_lrc_big.py` | 低秩的 V 解码矩阵校准；z 按文章算一次；M 所有层共用 | 1.7B→4B 约 3 分钟；8B→14B 2.9 分钟 |
| `cb_fast.py` | CacheBridge 初始映射：读一遍数据算出所有统计量，之后选层和拟合只用统计量 | 重新拟合约 20 秒（原 20 分钟） |
| `fit_lowrank_big.py` | 低秩拟合，统计量累积和主方向放到 GPU，岭回归仍在 CPU 上用 fp64 | 8B→14B 9.6 分钟（含采集） |

验证：
- 逐层路径和整模型路径的输出分布差 0，每次运行开头都会自检；
- 和旧版校准结果比较，修正量相对差：逐头前 25 层 < 1e-9，全头约 2%（bf16 存储的舍入），旧版测过的 50 题答案分别有 49/50、50/50 一致；
- 统计量拟合和官方 `fit_layer` 相比，E0 差 8e-7。

踩过的坑：
- 多卡时，每层处理前要 `torch.cuda.set_device`，否则矩阵分解会非法访问显存；
- FineWeb 上 M 只有 4096 个样本，而全头 8 层有 8193 维特征，M 必须用 fp64 累积；
- μ 很大时 fp32 Cholesky 会失败，要退回 fp64；
- 求 μ 的搜索过程中只用 fp32，只在最终的 μ 上做 fp64 修正（`fit_cb7` 后来的版本已改，旧版 12 层每档约 30 分钟）。

### 18.3 KL 训练翻译器（KV-Lingo / Hybrid-KV）

| | 我们（1.7B→4B） | Hybrid-KV 论文（8B↔4B） |
|---|---|---|
| 大海捞针 / 口令 | 2K 31.5%、8K 22% | 2–8K 100% |
| 验证集 KL（训练前 → 后） | 1.19 → 0.36 | 0.32 → 0.056 |

训练配置的差别：

| | 我们 | 论文 |
|---|---|---|
| 每步对话数 | 1 | 8 |
| 监督的续写长度 | 128 token | 最长 2048 或整段回答 |
| 学习率 | 固定 1e-4，没调 | 有调 |
| 初始映射的拟合数据 | FineWeb 文本 | 对话数据 |
| 偏置 | 不训练 | 训练 |

结论：我们的 KL 翻译器是训练不足的版本，现有表里的分数会低估这个方法。按论文配置重训，每个方向单卡约 3–4 小时，两卡数据并行约 1.5–2 小时。

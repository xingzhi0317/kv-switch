# 同设备多模型切换时的 KV cache 转换：实验报告

> 对应计划：`../PLAN.md`。代码、原始结果在服务器 `~/kvswitch/`，本地副本在本目录。
> 逐样本原始结果：`results/q_*.json`；汇总表（含 95% 置信区间）：`results/tables.md`；图：`figures/`。
> 实验日期 2026-11-13～14，单卡 RTX 4090 24GB。

## 0. 名词对照（报告里的编号都对应这些）

| 编号 | 中文说法 | 说明 |
|---|---|---|
| A / B | 原模型 / 切换后的模型 | A 的额度用完，换 B 继续聊 |
| P1 | 大换小 | Qwen3-4B → Qwen3-1.7B |
| P2 | 小换大 | Qwen3-1.7B → Qwen3-4B |
| P3 | 跨家族·稠密 | Llama-3.2-3B-Instruct → Qwen3-1.7B（分词器不同） |
| P4 | 跨家族·混合架构 | Llama-3.2-3B-Instruct → Qwen3.5-2B（18 层线性注意力 GDN + 6 层全注意力，分词器不同） |
| B0 / native | 从头重读 | B 对完整历史 prefill，质量基准（=100%） |
| none | 不看历史 | B 完全不看历史，质量下界 |
| B1 | 简化版 CacheBridge 式翻译 | 去 RoPE、相邻 3 个源层的**所有 head** 拼接、岭回归；V 按 B 的注意力概率加权校准。**与 CacheBridge 原文有多处不同，不是忠实复现**，见 §6.1 |
| B2 | NVIDIA 式翻译 | 同 B1 但 V 不做校准 |
| B3 | 翻译 + 重读 30%（RaReCache 式） | B1 之后让 B 重算偏差最大的 30% token |
| B4 | KV-Lingo 式（仅闭式初始化） | P3 用；按字符对齐 token，模板 token 由 B 自己算 |
| B5 | 混合架构翻译（2611.12062 式） | P4 用；全注意力层映射 KV，GDN 层预测输入后 B 自己 replay 递归 |
| B6 | 影子重读 | 预警期内 B 在后台对每轮新增内容做原生增量 prefill |
| C1 | 提前增量翻译 | 预警期内每轮结束后台把新增 token 翻译好 |
| C2 | 质检兜底（守卫 + 回退） | 用切换时能免费拿到的统计量判断翻译好坏，坏了就回退重读 |
| C3 | 后台升级 | 第一句用翻译 cache，后台原生重读，下一轮起换成精确 cache |
| C4 / ours_r64 | 我们训练的翻译器 | 在 B1 上加 rank-64 低秩残差，用 KL(B 原生 ‖ B 用翻译 cache) 训练，前缀长度随机 2K–8K |
| C5 | 边翻译边释放 | 按层翻译，某个 A 层不再被用到就立刻释放 |
| C6 | 翻译与新输入处理逐层重叠 | 两个 CUDA stream，第 l 层译完即开始处理新输入的第 l 层 |
| 保留率 | — | 方法得分 / 从头重读得分 |
| 有害翻转率 | — | 原生答对（F1≥0.5 或精确匹配）而切换后答错的样本占全部样本的比例 |

## 1. 主结论（先看这里）

1. **在本计划的质量阈值下（保留率 ≥98%、有害翻转 ≤5%），没有任何一种"翻译"方法达标**——包括我们复现的各基线（B1/B2/B3/B4/B5，均为简化复现，见 §6.1）和我们的翻译器（C4）。唯一的例外是 GSM8K（新问题与历史无关，翻译与否都一样）。因此 **M4 的验收标准 1、2 未达到**。
2. **我们的翻译器（C4，KL 自蒸馏低秩残差）在质量上明显强于我们实现的闭式基线（B1/B2）**，代价为零（残差合并进映射矩阵，推理开销与 B1 完全相同）：
   - 大换小 LongBench-8K：保留率 **91%**（B1 60%，B3 82%，不看历史 52%）；
   - 小换大 LongBench-8K：**65%**（B1 49%，B3 78%）；
   - CoQA 切换后第一轮：大换小 **46%** vs B1 24%，小换大 **34%** vs B1 20%（切换点 5/10 时：39%/48% vs 17%/23%，29%/33% vs 12%/16%）；
   - UltraChat 上 KL(原生‖切换后)：大换小 **0.12** vs B1 0.43、B3 0.20；小换大 **0.17** vs B1 0.41。
   但仍远低于 98%。**注意：B1 并非 CacheBridge 的忠实复现**（CacheBridge 没有公开代码，我们的实现在 head 选择、选层、V 校准上都与原文不同，更接近原文里作为反面诊断的"全 head 映射"——原文该诊断在 HotpotQA-E 上保留 60.6%，与我们 B1 在 LongBench 上的 60% 吻合）。因此**不能据此声称超过 CacheBridge**。
3. **翻译传得过去"大意"，传不过去"精确细节"**：找针（4K–16K）所有闭式翻译都是 **0%**，C4 只在 4K 有 8%（原生 94–100%），B3 重算 30% 也只有 4–29%。这是一个很强、很一致的负面结论，四组模型对都成立。
4. **与 CacheBridge 已知弱点的对照**：多轮 CoQA 上 B1 只保留 12–24%（CacheBridge 原文 Qwen3 8B→14B 为 31%，扩展映射器后 89%）；大换小方向我们没有观察到原文 Qwen3 14B→8B 那种 GSM8K 归零的崩溃，GSM8K 上所有方法都 ≈100%。由于 B1 不是忠实复现、模型规模也不同，这些只能算定性对照。
5. **后台升级（C3）是质量上最有效的组件**：第一句之后换成原生 cache，CoQA 第 2、3 轮保留率从 10–48% 回升到 **75–97%**（剩下的差距来自第一句的错误回答已经写进历史）。后台原生重读 32K 历史只需 2.7s，在 B 生成第一句回复（128 token 约 3.4s）期间就能完成，对 B 的解码速度影响 2–6%。
6. **速度与显存上，翻译与工程组件确实有效**：
   - 无预警切换（lead=0）时，翻译比从头重读快 **1.2–14 倍**（大换小 2K→32K：98→359ms vs 原生 98→2702ms；小换大 32K：491 vs 6826ms）；
   - C1 提前翻译使 T_switch 与历史长度无关：大换小 61–82ms，小换大 81–125ms；
   - C5 边译边释放把切换时额外显存从 B1 的 3.78GB 降到 **0.44GB**（大换小 32K），小换大 32K 从 5.04GB 降到 1.48GB（**M4 验收标准 3 达到**）；
   - C6 逐层重叠**没有收益**（8K 时 111 vs 111ms，32K 时反而更慢 455 vs 355ms），原因见 §4.3。
7. **和最强对手"影子重读（B6）"比，翻译的优势很小**：每轮 512 token 的后台工作，翻译占 GPU 18–28ms，影子重读 30–111ms（随历史变长而增大）；两者对前台 A 生成速度的干扰都在测量噪声以内；预警期显存两者相同（都要多存一份 B 格式 cache）。而影子重读的质量是 100%。**结论：有预警时影子重读 + 后台升级严格更优；翻译只在"无预警突然切换"时有价值，且必须接受明显的质量损失。** M4 验收标准 4 只能算"部分达到"（后台开销确实更低，但没有换来同等质量）。
8. **质检兜底（C2）失败**：试了 7 种在线统计量，在误报率 ≤10% 时只能抓到 12–22% 的有害翻转（要求 ≥70%），只对"明显坏掉"的翻译（故意加噪声、短距离找针）有效。按计划降级为离线规则（§3.4）。
9. **跨分词器（P3）闭式翻译基本无效**：LongBench 与"不看历史"持平（53% vs 50%），GSM8K 反而把正确率拉低到 73%（不看历史 89%）。**混合架构（P4）**：GDN 层 replay 是关键（去掉 replay 就等于不看历史），但 replay 本身要占原生 prefill 约 70% 的时间，16K 时只快 1.4 倍。

| | 大换小 第2轮 | 第3轮 | 小换大 第2轮 | 第3轮 |
|---|---|---|---|---|
| B1 一直用翻译 cache | 31% | 22% | 21% | 22% |
| C4 一直用翻译 cache | 47% | 42% | 38% | 35% |

### 3.4 质检兜底（C2，M3）

用 B1、B2、B3、C4 以及两个故意降质的翻译器（`noise0.5`、`noise2`：1 个源层 + 高斯噪声）构造"好/坏"cache，覆盖 CoQA、LongBench、找针、GSM8K。7 种在线统计量：

| 统计量 | 含义 | 大换小 AUC / TPR@FPR≤10% | 小换大 |
|---|---|---|---|
| s1 | 新输入上 B 的平均 NLL | 0.61 / 0.17 | 0.63 / 0.22 |
| s2 | s1 − 不带历史时的 NLL | 0.50 / 0.16 | 0.45 / 0.21 |
| s3 | 新输入最后 8 个 token 的预测熵 | 0.56 / 0.17 | 0.62 / 0.20 |
| s1l | 新输入最后 32 个 token 的 NLL | 0.61 / 0.16 | 0.65 / 0.21 |
| s4 | KL(A‖B)：A 的 cache 还在，让 A 也读一遍新输入 | 0.60 / 0.16 | 0.61 / 0.22 |
| s5 | A 与 B top-1 不一致率 | 0.60 / 0.17 | 0.65 / 0.21 |
| s6 | −s2 | 0.50 / 0.12 | 0.55 / 0.18 |

分任务看（tables.md），只有"坏得很明显"的情况（加噪声的翻译器、4K 找针）统计量才有用（AUC 0.76–0.91）；对"看起来流畅但答错"的情况基本区分不出。有一个有意思的现象：s2 的 AUC ≤ 0.5（部分子集明显低于 0.5），即坏样本的 NLL 反而更低——印证计划 §0.6 说的"被带偏成源模型"：翻译后的 B 对用户输入**更不意外**，而不是更困惑。

**降级为离线规则**：按模型对和任务类型，所有需要复述历史细节的任务（CoQA、找针、LongBench）在 4 组模型对上都达不到 98%，因此离线规则等价于"这些场景一律不用翻译 cache 直接回答，改用原生 cache（影子重读或从头重读）"；只有"新问题与历史无关"的场景（GSM8K 式）可以直接用翻译 cache——但这一点在线无法判断。图：`figures/guard_roc_P*.png`。

### 3.5 跨家族（M5）

**P3：Llama-3.2-3B → Qwen3-1.7B（跨分词器，B4 闭式初始化）**

| 任务 | 不看历史 | B4（3 源层） | B4k1（1 源层） |
|---|---|---|---|
| UltraChat KL↓ | 0.69 | 0.91 | 0.56 |
| CoQA k=1 | 4% | 24% | 17% |
| LongBench-8K | 50% | 53% | 50% |
| 找针 8K | 0% | 0% | 0% |
| GSM8K | 89% | 73% | 99% |

跨分词器时 3 个源层反而比 1 个更差（过拟合到对齐噪声），而且在 GSM8K 上翻译 cache 比不看历史还差——翻译引入的错误历史会干扰与历史无关的新问题。字符对齐本身是正确的（单测见 `src/xalign.py` 的检查脚本），模板 token 由 B 自己重算。

**P4：Llama-3.2-3B → Qwen3.5-2B（GDN 混合架构，B5）**

| 任务 | 不看历史 | B5（GDN replay） | B5 去掉 replay |
|---|---|---|---|
| UltraChat KL↓ | 0.43 | 0.22 | 0.34 |
| CoQA k=1（100） | 3% | 42% | 2% |
| LongBench-8K（100） | 49% | 60% | 43% |
| 找针 8K（50） | 0% | 0% | 0% |

GDN 层的递归状态是关键：只翻译 6 个全注意力层、GDN 状态从零开始，效果等于不看历史。用 B 自己真实的层输入做 replay（"神谕"测试），可以 93% 还原原生的下一 token（误差来自 bf16 与分块 kernel），说明 replay 管线本身正确，损失来自"预测层输入"这一步（各层验证相对误差 4%–28%）。

## 4. 系统测量（M0、M4）

计时方法：`torch.cuda.Event`，每配置预热 5 次、正式 20 次，报中位数（p50）和 p95；新输入 128 token；每次测量前 reset 峰值显存。T_switch = 翻译（或重读）+ 处理新输入 + 第一步解码。

**重要说明**：所有方法共用同一套手写 PyTorch 前向（无 CUDA graph），单步解码被 Python kernel 启动开销主导（GPU 实际 ~7ms，墙钟 12–37ms，每步约 1700 次 kernel 启动）。这部分对所有方法相同，但会压缩短历史时的相对差距。生产引擎（CUDA graph）下，短历史时翻译相对重读的优势会更明显。

### 4.1 M0：显存预算与 prefill 时间

| 模型对 | 两模型 bf16 权重 | 2K | 4K | 8K | 16K | 32K（两份 cache） | 32K 能放下? |
|---|---|---|---|---|---|---|---|

### 4.3 C6 重叠为什么没有收益

新输入只有 128 token，其处理本身被 kernel 启动开销主导（CPU 侧），而翻译是少量大矩阵乘（GPU 侧）。两个 stream 并行时，翻译占满 SM，新输入的小 kernel 只能见缝插针；同时第 l 层必须等第 l 层翻完，关键路径基本等于"翻译总时间 + 最后一层的新输入"。32K 时重叠反而慢 100ms（额外的 event 同步与 SM 竞争）。按计划如实报告：**C6 无收益**。

### 4.4 后台开销：提前翻译（C1）vs 影子重读（B6）

每轮 512 token 新增内容，在后台低优先级 stream 上处理：

| | 大换小 2K | 4K | 8K | 16K | 小换大 2K | 4K | 8K | 16K |
|---|---|---|---|---|---|---|---|---|
| C1 翻译 GPU ms/轮 | 18 | 19 | 18 | 18 | 25 | 25 | 26 | 28 |
| B6 影子重读 GPU ms/轮 | 30 | 30 | 31 | 47 | 46 | 55 | 74 | 111 |
| 预警期额外显存（两者相同） | 0.27GB | 0.49 | 0.93 | 1.80 | 0.4 | 0.6 | 1.2 | 2.3 |

- 对前台 A 生成速度的干扰：两者都在测量噪声以内（前台解码本身被 CPU 启动开销主导，±50ms 的波动掩盖了差异），**无法得出"翻译干扰更小"的结论**。
- 浪费（预警了但最终没切换）：每轮浪费的 GPU 时间就是上表的数值；按 `lead_turns` ∈ {1,2}、p_switch ∈ {0.3,0.6,1.0} 换算，期望浪费 = lead_turns × (1−p_switch) × 每轮开销，最多 2×0.7×111ms ≈ 155ms/次对话（影子重读、小换大 16K），对一张卡来说可以忽略。（这里是按实测数值解析换算的，没有做端到端模拟。）
- **结论**：翻译的后台 GPU 时间确实低 1.6–4 倍，但两者的绝对值都只有几十毫秒，远小于用户思考时间（秒级），且显存代价相同；而影子重读得到的是精确 cache。在有预警的场景下，影子重读严格更优。

| 大换小 8K | 339ms | 26.4 / 27.4ms | 3.38 / 3.45s |

### 6.1 我们的 B1 与 CacheBridge 原文的差异（事后核对原文，2026-11-14）

CacheBridge（arXiv 2609.00891 v2）**没有公开代码**。按原文核对，我们的 B1 有以下不同，因此 B1 只能算"简化的 CacheBridge 式"基线：

| | CacheBridge 原文 | 我们的 B1 |
|---|---|---|
| 目标 head 的输入 | head-local：只读每个选中源层里**同编号**的那一个 KV head（k×d 维） | 选中源层的**所有** KV head 拼接（k×H×d 维）——原文把这种"全 head 映射"当作反面诊断，HotpotQA-E 只保留 60.6% |
| 选源层 | 每个目标层按单层回归 R² 选 top-k，不要求相邻；Qwen3 8B→14B k=8，其他对 12–20 | 按深度比例取中心附近相邻 3 层 |
| 岭回归 | 中心化，λ=0.01 | 不中心化，λ 由验证集选 |
| 初始拟合数据 | FineWeb-Edu 500×1024 token，步长 4，共 12.8 万位置 | UltraChat+C4 各半，64×2048 token |
| V 校准 | 拟合"映射后注意力输出 − 原生注意力输出"的残差（用映射后的 K 和新输入自身的 KV 计算），只修 V 映射，带能量约束（≤1% 初始残差能量），逐层顺序求解（用前层已修正的状态），FP64 | 用 B 原生 K 的注意力概率做加权岭回归，无残差、无约束、不逐层 |
| 校准查询 | 24 篇 QuALITY 文档 × 4 个真实问题 | 序列中随机 256 个位置 |
| 实现 | SGLang，2048 token 分块直写分页 cache，与传输流水重叠，FP32 映射 | 自写 PyTorch，8192 分块，bf16 映射 |
| 模型/硬件/任务 | Qwen3 8B→14B 等 5 对（≥3B），H800 TP4；11 个任务（HellaSwag、WinoGrande、ARC-C、MMLU、MMLU-Redux、GSM8K 8-shot、SQuAD、QuALITY、Qasper、HotpotQA-E、CoQA）+ τ-bench | Qwen3 1.7B↔4B，单卡 4090，对话格式任务 |

原文关键数字（供对照）：小换大平均保留 97.94%（对话/推理）、102.94%（RAG）；V 校准把平均保留从 72.26% 提到 99.94%；Qwen3 8B→14B 的 CoQA 只有 31.07%，换成 8.6 亿参数的扩展映射器后为 89.11%；大换小 Qwen3 14B→8B 是弱点（GSM8K 0%、HotpotQA 2.28%、CoQA 9.37%）。

要声称超过 CacheBridge，需要：(1) 按上表忠实复现；(2) 在原文的设置（至少 Qwen3 8B→14B 和几个原文任务）上跑出接近原文的数字；(3) 再在同一套评测上与我们的方法对比。

## 7. 局限性

- 只覆盖**同设备共驻**（单卡），不含跨卡/跨机传输；跨卡时翻译相对传输的收益会完全不同，需在 NVLink 机器上另做。
- 模型规模 ≤4B；结论（尤其是"翻译传不了细节"）是否适用于更大模型未验证——CacheBridge 在 8B/14B 上的数字明显更好。
- 评测使用非思考模式（`<think>\n\n</think>`），历史回答用数据集给的参考答案而非 A 生成的回答。
- 计时用手写 PyTorch 前向，无 CUDA graph / 融合 kernel；绝对数值偏慢，短历史时相对差异被压缩。
- 每种设置的样本数少于计划的 200（见决策记录）；保留率差 1–2 个百分点时置信区间重叠，请看 tables.md 的区间。

## 8. 决策记录（计划没覆盖或有偏离的地方）

1. **样本数**：UltraChat、LongBench、GSM8K（Case 1）为 200；CoQA 每个切换点 100 段对话（每段切换后 3 轮，共 300 个回答）；找针每个长度 50 条（计划 100）；P3 GSM8K 100、P4 各任务 100/50。原因：一晚上的 GPU 时间。
2. **找针 32K 作废**：Qwen3-1.7B 在 32.6K token 上原生只有 2%（超出其可靠长度）；小换大 32K 两份 cache 加激活放不下（OOM，与显存预算表一致）。
3. **B1 的输入特征**：计划写"k 个源层对应 head 的拼接"，但不同大小模型的 head 并不对应，我们改为"k 个源层**所有** KV head 的拼接"→ 每个目标层一个仿射映射（等价于每个目标 head 一组列）。V 校准：最小化 ‖P·X·W − P·V_B‖，P 为 B 自己的注意力概率（每序列随机 256 个 query 位置）。
4. **Sink**：所有翻译方法（含基线）位置 0 都用 B 自己的 KV（代价一个 token），保证公平。
5. **B3 的 token 选择**：RaReCache 的"秩分歧"细节不可得，改用"翻译后与 B 精确 layer-0 KV 的相对偏差"（layer-0 KV 只依赖 embedding，几乎免费），并把 layer-0 全部换成精确值；选中的 30% token 逐层重算（CacheBlend 方式）。
6. **B4 只做了闭式初始化**，没做 KV-Lingo 的 KL 自蒸馏；字符对齐简化为"每个 B token 取覆盖其最后一个字符的 A token"。
7. **P4 模板 token**：计划要求让 B 自己算模板 token，但 GDN 是顺序递归，无法只重算中间几个 token；改为按位置比例映射到 A 的模板 token。P4 目标模型选 Qwen3.5-2B（存在 0.8B/2B/4B，2B 与 Llama-3B 一起放得下）。
8. **C2 降级**：未达到 M3 标准，降级为离线规则（§3.4）。
9. **C1/B6 的 lead_turns × p_switch 扫描**用实测的每轮后台开销做解析换算，没有做端到端模拟（§4.4）。
10. **用户思考时间**：未用到真实分布（C3 在回复生成期间就完成，与思考时间无关）。
11. **融合 Triton kernel、vLLM/SGLang 接入（加分项）均未做**。翻译本身是每层两次大 GEMM + 逐元素 RoPE，融合的收益上限是 RoPE 那部分（估计 <20%）。
12. **增量翻译 vs 一次性翻译**：数值上不是逐位一致（bf16 下最大绝对差 2.0/4.0，来自 K 数值较大时不同矩阵形状的 GEMM 分块舍入，约 1 ulp）；C5 边译边释放、C6 重叠与基线**逐位一致**（最大差 0）。
13. **M0 显存表的 bug**：P2/P3 的 `weights_GB` 字段被前一对模型的残留显存污染，报告中按参数量更正。
14. **评测中途的两个 bug**（多轮时 cache 余量不足、无历史 NLL 的临时 cache 尺寸错误）导致部分 CoQA 任务中断，修复后用 resume 补跑，已完成样本不受影响（结果按样本 id 合并）。
15. **计时环境**：服务器与他人共用（另外 4 张卡有他人任务），CPU 负载 4–12，会给 kernel 启动开销引入噪声。

## 9. 下一步

场景已改为：不假设 A、B 同机，计时从"B 拿到 A 的 KV cache"开始，只优化 B 的 TTFT（见 `../PLAN_v2.md` 与后续讨论）。据此：
1. 提前翻译、影子重读、质检兜底不再使用；翻译器（C4）、边译边释放（C5）、后台升级（C3，可改为"回复中途换原生 cache"）保留。
2. **第一步是忠实复现 CacheBridge**（§6.1），在它的设置上对齐数字，然后才能做 SOTA 对比。
3. head 按编号映射没有原理依据（head 顺序可任意置换而模型不变）。建议先做诊断：目标 head × 源 head 的 R² 矩阵，看对角线是否特殊；并测"随机打乱源 head 顺序"对 CacheBridge 的影响。改进方向：按数据选 (层, head)、按注意力模式匹配、head-local 主映射 + 跨 head 低秩残差。
4. 翻译传不了精确细节（找针 0–8%）：尝试少量关键 token / 最近窗口的原生重算。
